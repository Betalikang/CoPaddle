## 3. 系统架构

```
浏览器 ── HTTP ──> Caddy(:80) ──> web / Next.js(:3000) ── TCP ──> PostgreSQL 16(:5432)
                                     │
                                     └── 内网 HTTP + X-Internal-Secret ──> algo / FastAPI(:8000)
```

- **双服务 + 共享数据库**：web 拥有全部写权限；algo 只做计算，**不连库**，输入数据由 web 组装后 POST 过去（`algo/app/config.py` 的 `database_url` 字段在代码中从未被使用）。
- **建表与迁移统一由 web 侧 Drizzle Kit 管理**（`web/lib/db/migrations` 共 10 个迁移文件，0000–0009）。
- **服务间鉴权**：`web/lib/algo/client.ts` 每次调用带 `X-Internal-Secret`；algo 侧 `algo/app/deps.py` 的 `require_internal_secret` 未配置密钥时 **fail-closed 返回 503**，不匹配返回 401。

### B-06 分组编排（M1，核心算法）

**前端**：`/dashboard/courses/[id]/grouping`，@dnd-kit 拖拽 + recharts 雷达图；拖一下即调 `/internal/grouping/score` 出四维得分。

**服务层** `web/lib/services/grouping.ts`（842 行）：
`runGrouping(courseId, teacherId)` → `getSettings` → `prepareInput`（只取 `role ∈ {member,captain}` 且 `status='active'`，教师/助教不进组）→ 插 `grouping_runs(mode:'cpsat', status:'running')` → `callAlgo('/internal/grouping/solve', {time_limit_seconds: 10, allow_cross_class, forbidden_pairs, edges, ...}, 60000)` → 回写 run（`solverStatus = degraded?'greedy':'optimal'`、`durationMs`、`solutionsFound`）→ 落 3 条 `grouping_plans`（含四维分与权重快照，`originalGroups` 保留初始态以支持 reset）。

**算法** `algo/app/algorithms/grouping.py`（609 行，CP-SAT）：

三套策略预设 `STRATEGY_PRESETS`：

| key | 名称 | (skill_cover, weak_tie, balance, history_avoid) |
|---|---|---|
| `skill_first` | 方案A · 能力互补优先（推荐） | (1.5, 0.6, 1.2, 1.0) |
| `weaktie_first` | 方案B · 弱连接优先 | (1.0, 1.6, 1.0, 0.8) |
| `fairness_first` | 方案C · 公平优先 | (1.0, 0.6, 1.8, 1.2) |

每个策略共享时间预算 `per_plan_limit = max(time_limit / 3, 1.0)`；`n > MAX_STUDENTS_FOR_CPSAT(200)` 直接走贪心并置 `degraded=True`。

**硬约束**（`_solve_once`）：H1 组规模 [min,max]、H2 不可同组（`AddAtMostOne`）、H4 不混班（每组一个班级布尔，`sum(cg) <= 1`，避免 O(n²·G)）、H5 每组人数与一次性分配（`AddExactlyOne`）。
**软目标**（全部线性化，SCALE=1000 取整，因 ortools 线性表达式不支持除法）：

```
obj = skill_coef·Σcover − weak_coef·2Σstrong_pairs − hist_coef·2Σhist_pairs
      − balance_coef·(hi−lo) − size_coef·Σ|size_g − n//G|
```

`skill_coef = round(SCALE·w_skill·1000/(n_dims·G))`、`weak_coef`/`hist_coef` 同式除以 `all_pairs`、`balance_coef = round(SCALE·w_balance·1000/total_power)`、`size_coef` 用 `(w_weak_tie + w_history_avoid)`。
求解参数 `num_workers=4`、`max_time_in_seconds=max(time_limit,1.0)`；非 OPTIMAL/FEASIBLE 则返回 None 触发贪心兜底。

> 源码长注释记录了一处**已修复的目标函数 bug**：旧式把凸项 Σ size_g(size_g−1) 以正号计入两次，等价于奖励规模不均（12 人 3 组会偏向 [5,4,3] 而非 [4,4,4]），现改为只留惩罚项 + 显式 `abs_dev`。

**评分** `score_plan`（0–100，四维）：

- 技能覆盖 `= 100·(0.7·均值 + 0.3·最小值)`，某维度满分为「组内至少一人该能力 ≥ 3」
- 弱连接 `= 100·mean(1 − 强连接对数/组内总对数)`（`edge weight ≥ 0.5` 记强连接）
- 均衡 `= 100·max(0, min(1, 1 − std/mean))`，组实力 = Σskills
- 历史规避 `= 100·(1 − mean(历史同组对数/组内总对数))`
- `total` 按权重归一加权

**兜底** `_greedy_groups`：`divmod` 定目标人数 → 三遍放置（最空可行组 → 移走冲突者 → 三向轮换），结果必须过 `validate_plan`，否则 `detail="约束组合无可行解（常见原因：不可同组配对过多）"`；降级成功标 `detail="快速模式（贪心兜底）"`。前端不可行提示：`"${n} 人无法分成 ${num_groups} 组且每组 [${min}, ${max}] 人，请调整组数或规模约束"`。

**人工微调**：`applyMoveToGroups` 以成员**实际所在组**为准（`next.findIndex(g => g.includes(userId))`），不信任前端传来的 from；`routers/grouping.py` 的 `_apply_move` 同样按 user_id 真实归属移动，支持 `swap_with`。

> ⚠ 已知伪实现：方案 B / C 的初始快照由 web 侧 `buildPlanSnapshots`（`grouping.ts:334-353`）伪造——A 原样、B 相邻组尾部互换、C 每组 shift 一人，**未经 algo 评分**；仅在「plan.groups 全空」自愈时回填。

### B-08 任务拆解（M3，LLM 调用点 1）

`services/tasks.ts:65 generateTaskPlan(groupId, captainId, input)`：
已存在计划时先返回 `{needConfirm:true}`；确认后 `callAlgo('/internal/ai/decompose', {assignment_text, group_size}, 120000)`；`AlgoServiceError` → 降级 `{aiUnavailable:true, message}`（「AI 暂不可用，可手工创建」）；成功则在**一个事务**里边删旧计划/契约边写 `task_plans + tasks + task_deps + contracts + contract_glossary`。

`algo/app/ai/decompose.py`：SYSTEM_PROMPT 要求「任务 2–8 小时、≤12 个、deps 显式、id 形如 T1/T2、术语表 ≥2 条含单位与口径」；后置校验 `validate_decomposed`（重复 id / 悬空依赖 / 成环），失败**带问题反馈重试 1 次**，仍失败则连同 `validation_problems` 落库并标 `validated=false`（界面高亮人工修正，不静默丢弃）；结构非法 → `LlmUnavailableError` → 路由 503。

关键路径 `markCriticalPath(groupId, conn = db)`（`:217`）：把任务与 deps 送 `/internal/graph/critical-path`，回写 `tasks.onCriticalPath`。**必须传事务连接 `tx`**——源码注释说明：走全局 db 的另一连接读不到未提交任务（首次生成永远空），重新生成时还会被行锁挡住形成应用层死锁。成环时抛错而非清零（清零会让归因 `cp_total` 归零、学分凭空消失）。

### B-10 进度感知与健康度（M4/M5）

- 信号 `progress_signals`：**唯一真实写入点**是 `services/tasks.ts:482 changeTaskStatus`（`signalType:'status_changed'`，payload `{from,to}`），另有种子脚本写 `segment_edited`。`recordSignal` 定义在 `health.ts:89` 但全仓无其他调用者——**失联判定只由任务状态变更驱动**。

- `algo/app/algorithms/scheduling.py`：`DAILY_CAPACITY_HOURS = 6.0`
  - 关键路径：**拓扑排序 + 最长路径**（不是 networkx 最短路径，见 `routers/graph.py:4` 注释），成环返回 `error` 字段而非抛异常

### B-11 冲突检测（M6，LLM 调用点 2）

`algo/app/ai/conflict.py`：`SIM_DUPLICATE = 0.85`、`SIM_UNRELATED = 0.30`；jieba 分词 + `rapidfuzz.fuzz.token_set_ratio/100`。
相似度 **≥0.85 判「内容重复」、<0.30 判「无冲突」，两者都不调模型**（`model="rule:rapidfuzz"`）；中间区间才调 LLM。reason 少于 8 字符或非 JSON 则重试；降级时 `degraded=True` 且 model 留空。

web 侧 `services/conflicts.ts` 另做**依赖图过滤**（已修）：import `taskDeps` 建 `successors` 邻接表，`reachableDownstream` 求传递闭包，只保留下游未完成任务，标题「阻塞/延期，波及 N 个下游任务」。
⚠ 去重只认 `status='open'`（`:85-89`），一旦进入 `analyzing` 同一任务会重复报冲突。

### B-12 重规划

`services/replan.ts buildOptions`（`:289`）三方案：
- **A 重新分配**：排除现主责人，按 `loadRatio` 升序取最空 2 人，`estImpactDays=0.5`
- **B 缩减范围**：只收 `TYPE_WEIGHT[deliverableType] <= 0.5`（slide 0.2 / figure 0.4 / table 0.5 / document 0.7 / dataset 0.8 / code 0.9），`est=1`
- **C 组间补位**：`borrow` 空数组占位，`est=2`，文案「需要教师授权：从健康度 > 80 且负载 < 60% 的其他小组借调技能匹配成员」

触发阈值**硬编码** `{ delayTriggerDays: 2, idleTriggerDays: 3 }`（未读 `course_settings`）；负载率 `min(openHours / 42, 1)`（42 = 一周可投入工时）。
并发安全：`adoptOption` 用「先 UPDATE 抢占 `status='pending'`」，`claimed` 为空返回「该重规划已处理」；`rejectEvent` 把状态守卫写进 WHERE。
事务内自建 `groupMemberIdsTx / courseTeacherIdTx / notifyTx`（`notifications.ts` 硬绑全局 db，会在事务提交前发通知——源码注释记录该决策）。
⚠ `scope_cut` 在 `:519-527` **直接 `update tasks set status='cancelled'`**，绕过 `TASK_TRANSITIONS` 且不写 `task_status_events`。

### B-13 交付物溯源

`services/artifacts.ts`：
- 字数口径 `wordCount = text.replace(/\s+/gu,'').length`（去空白字符数）
- 分段指纹 `hashContent = sha256(text).hex.slice(0,16)`
- `saveVersion`（`:40`）：按 `seq` 对齐 diff —— 新 seq → `create`（author=提交人）；hash 相同 → 原样保留；hash 不同 → `revise`（`revised_by`、`revised_count+1`）；旧版有本版无 → `delete` 记录不写入。**段落归属靠平台内撰写行为天然沉淀，不靠学生自报**。
- `compileFinal`（`:297`）：先 `select ... for('update')` 锁小组行（防双击各插一份终稿、`max+1` 撞唯一键），来源排除既有终稿自身（否则层层嵌套），复用同一 artifact、版本号自增，artifact 与 version 两步写库同事务。`isCompiledFinal = type==='final' || (isFinalDeliverable && title===FINAL_TITLE)`。

### B-14 贡献归因（M6 之外的另一个核心算法）

`algo/app/algorithms/attribution.py`（204 行，`web/lib/services/contributions.ts` 599 行是其调用方）：`UNCERTAINTY_SCALE = 6.0`、`MAX_SPREAD = 8.0`。
三类证据：**A 产出物**（主责全权 `words_authored` + 协作半权 `0.5·words_revised`）、**B 过程**（0.35 按期率 + 0.30 关键路径 + 0.20 返工惩罚 + 0.15 补位）、**C 同伴**（去极值中位数映射 `(median−1)/4`）。同伴整体缺席时按 `w_a : w_p` 重分并标 `peer_missing`。
输出 `point / low / high / confidence / comp / fair_share_ratio / warning`；不确定度 `= 6.0·(1−coverage)·(1−agreement)`，`high = min(point+unc, point+8)`。

**铁律：永不输出单一分数**——`contributions.ts:244-256` 只落 `lowPct/highPct`（`clampPercentRange`），注释原文「系统只存区间，永不存点估价（铁律）」；同写 `onTimeCount/delayCount/reworkCount/reviewCount`，同伴证据 `refType='peer_review'`、`refId=peer_reviews.id` 可逐条下钻。
其余能力：`getGroupLedger`（小组账本）、`getSnapshotEvidence`（证据下钻）、`reviewSnapshot` → 写 `attribution_reviews` + 审计 `attribution_review`、`lockGroupSnapshots`（只更新 `isLocked=false` 且限定 groupId，返回新锁定条数、审计 `attribution_lock`）、`submitAppeal`/`handleAppeal`（申诉闭环）。
