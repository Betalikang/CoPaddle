### 1.13 relations 覆盖缺口

### 1.14 数据库迁移

`web/drizzle.config.ts`：

```ts
schema: './lib/db/schema.ts'
out: './lib/db/migrations'
dialect: 'postgresql'
dbCredentials: { url: process.env.POSTGRES_URL! }
```

### 2.2 会话签发与校验

`web/lib/auth/session.ts`：


- 库：**jose**（`SignJWT` / `jwtVerify`），算法 **HS256 对称密钥**，密钥来自 `process.env.AUTH_SECRET`。
- 有效期：`signToken` 内 `.setExpirationTime('1 day from now')`；`setSession` 内 cookie `expires` 亦为 now+24h。
- Cookie：**名字 `session`**，选项 `{ expires, httpOnly: true, secure: process.env.COOKIE_SECURE !== 'false', sameSite: 'lax' }`。注释说明纯 HTTP 部署（裸 IP 演示）需 `COOKIE_SECURE=false`。
- 载荷极简：只有 `{ user: { id }, expires }`，**不含角色、不含课程**。
- 变量名 `encryptedSession` 有误导性：JWT 是**签名**而非加密，payload 可被客户端 base64 解码。

校验路径 `web/lib/auth/../db/queries.ts:7`：

```ts

  if (!session?.value) return null;
  try { const data = await verifyToken(session.value); ... } catch { return null; }

  // 再 select * from users where id = ? and deleted_at is null limit 1
```

`getUser()` **每次调用打一次数据库**（会话校验 + 用户行），是整条请求链最热的查询。`verifyToken`（`session.ts:33`）本身没有 `try/catch`，也没有对 payload 做 zod 校验，只 `return payload as SessionData`；依赖调用方兜异常。

## 3. algo 客户端

`web/lib/algo/client.ts`（93 行）：

```ts
const ALGO_URL = process.env.ALGO_SERVICE_URL ?? 'http://127.0.0.1:8000';

  body: unknown,

  constructor(message: string, readonly status?: number)
}
```

- **只支持 POST**（没有 GET 分支），`fetch(`${ALGO_URL}${path}`, { method: 'POST', ... })`。
- 请求头：`'Content-Type': 'application/json'` + **`'X-Internal-Secret': ALGO_SECRET`**（共享密钥鉴权头）。
- 超时：`AbortController` + `setTimeout(timeoutMs)`，默认 30s，由调用方覆盖。
- 其他：`cache: 'no-store'`。
- 失败策略：**一律抛 `AlgoServiceError`，客户端层不做降级**。文案三态：
  - HTTP 非 2xx → `算法服务返回 ${res.status}：${text.slice(0, 200)}`（带 `status`）
  - `AbortError` → `算法服务调用超时（${timeoutMs}ms）`
  - 其他网络错误 → `算法服务不可达：${msg}`
- 每次调用后写 `ai_call_logs`（`logCall`，动态 `import` db 避免循环依赖）：`endpoint = path.replace(/^\/internal\//, '').slice(0, 50)`、`status: 'ok' | 'failed'`、`latencyMs`、`error` 截断 500、`callerId/courseId/groupId` 取自 `ctx`。日志写入整体 `catch {}` 静默，注释"日志失败不影响业务"。

## 5. 状态机

### 5.1 任务状态 `tasks.status`

取值：`todo` | `doing` | `blocked` | `reviewing` | `done` | `cancelled`（default `'todo'`，`schema.ts:430`；zod 同构 `validation/tasks.ts:33`）。

```ts
export const TASK_TRANSITIONS: Record<string, string[]> = {
  todo: ['doing', 'blocked', 'cancelled'],
  doing: ['reviewing', 'blocked', 'cancelled'],
  blocked: ['doing', 'cancelled'],
  reviewing: ['done', 'doing', 'cancelled'],

  cancelled: []
```

即：`todo → doing|blocked|cancelled`；`doing → reviewing|blocked|cancelled`；`blocked → doing|cancelled`；`reviewing → done|doing|cancelled`；`done`/`cancelled` 终态（不可复活）。

强制点**唯一**：`web/lib/services/tasks.ts:407` `changeTaskStatus`（`TASK_TRANSITIONS[task.status] ?? []`，不许则返回 `{ ok: false, reason: \`不允许从 ${task.status} 直接变为 ${input.toStatus}\` }`）。

**绕过点**：`web/lib/services/replan.ts:437` 直接 `update tasks set status = 'cancelled'`，不经状态机、不写 `task_status_events`、不写 `progress_signals`。若以后要复活被砍任务，状态机会直接拒绝（`cancelled: []`）。

### 5.2 分组方案状态

- `grouping_runs.status`：`running`（insert 初值）| `ok` | `infeasible` | `timeout` | `error`。迁移：`running → ok | infeasible | timeout | error`（`grouping.ts:211` 内先 insert `running`，algo 返回后写 `ok`/按 status 原样落库，`catch` 写 `error`）。`solverStatus` 另一维度：`optimal` | `greedy`（由 `degraded` 推导）。
- `grouping_plans`：**无 status 列**，只有布尔 `isSelected` + `selectedAt`/`selectedBy`。同一 run 内互斥（`selectPlan` 事务中把其它 plan 置 false）。
- `groups.status`：`forming`（default）| `active` | `dissolved` | `merged`。实际迁移：`— → active`（`selectPlan` insert 时直接给 `'active'`，故 `forming` 永不出现）、`active → dissolved`（`dissolveGroup`）。**`merged` 与 `groups.mergedInto` 无任何写入点 → dead code**；代码里没有"并组"实现。

### 5.3 重规划状态

- `replan_events.status`：insert `pending`（`replan.ts:178`）→ `adopted`（`adoptOption`，同时写 `adoptedOptionId`/`handledBy`/`handledAt`）或 `rejected`（`rejectEvent`）。
- 守卫强度不对称：`adoptOption` 检查 `event.status !== 'pending'` → `{ error: '该事件已处理' }`；`rejectEvent` **完全不检查当前状态**。
- 无 `expired`/`cancelled` 态；事件不会因超时自动失效。
- `replan_options` 无状态，仅 `eventId` 从属。

### 5.4 互评轮次状态 `peer_review_rounds.status`

取值：`scheduled`（default）| `open` | `closed` | `published`。

设计迁移：`scheduled → open → closed → published`（`replan`/`peer-reviews.ts:76,86,102` 的注释分别写明）。

实际实现：`openRound`(:77)、`closeRound`(:90)、`publishRound`(:103) 全是**无条件 `update ... set status = ?`**，没有前态校验 —— 因此 `published → open`、`scheduled → published` 都能成功。唯二的有效守卫在别处：`submitReview` 要求 `status === 'open'`；`getPeerReviewDetails` 只取 `status in ('closed','published')` 的最新一轮。

### 5.5 冲突状态 `conflicts.status`

取值：`open`（default）| `analyzing` | `resolved` | `dismissed`。

迁移：`open → analyzing`（`analyzeConflict`，`conflicts.ts:167`）→ `resolved` | `dismissed`（`resolveConflict`，按 `action === 'dismiss'` 分流）。`detectConflicts` 的"已报过去重"集合只认 `status='open'` —— **一旦冲突进入 `analyzing`，同一任务会被再次报一条新冲突**。

### 5.6 申诉状态 `attribution_appeals.status`

取值：`submitted`（default）| `reviewing` | `accepted` | `rejected` | `partially_accepted`。`handleAppeal`（`contributions.ts:523`）直接 update，**无状态机、无迁移校验**，`submitted → accepted`、`accepted → submitted` 均可行。

### 5.7 其他枚举（无迁移约束）

- `courses.status`：`draft` | `active` | `archived`（default `draft`）。`updateCourse`（`courses.ts:117`）**不校验 archived 只读语义**，`archived` 可被任意改回 `draft`；`schema.ts:95` 注释里"archived 只读"仅是文档。
- `artifacts.status`：`draft`（default）→ `review`（`compileFinal` 建终稿时）→ `submitted`（`submitFinal`）。无回退保护。
- `attribution_reviews.isLocked`：布尔业务锁（见 §4.8）。
- `contribution_snapshots.confidence`：`low`/`medium`/`high`（default `low`，值由 algo 返回）。
- `task_assignments.raci` 与 `group_members.duty`：`lead` | `contributor` | `reviewer`（两套同构枚举，未共享常量）。
- `notifications.priority`：`low` | `normal`（default）| `urgent`；`channel`：`inapp`（default）| `email` | `wechat`。

## 6. Web 侧自算公式（服务层确实自己算分的部分）

### 6.1 健康度总分 `overallOf` —— Web 侧唯一的合成评分公式

`web/lib/services/health.ts:190-194`：

```ts
function overallOf(s: typeof groupHealthSnapshots.$inferSelect): number {
  return Math.round(
    0.4 * Number(s.blockedScore) + 0.3 * Number(s.idleScore) + 0.3 * Number(s.overloadScore)
  );
}
```

权重 **阻塞 0.4 / 空闲 0.3 / 过载 0.3**，四舍五入取整，输出 0–100。三维持定义均为"越高越好"（default `'100'`），故 `overall` 也是越高越好。algo 返回的 `overall` 字段**被 Web 侧忽略**（`getCourseHealthOverview` 用 `overallOf` 重算；`computeGroupHealth` 存库时也未写 `overall` 列，因为表里没有该列）。

配套：

- `onTrackRatio = onTrack / openTasks`（`health.ts:98` 内），`openTasks` 排除 `done`/`cancelled`，`onTrack` = 未被 algo 标 `blocked` 的数量。
- 预警阈值：`overall < 80 || diagnosis.length > 0`（`health.ts:200`），按 overall 升序。

### 6.2 分组策略权重与"实时得分"

`web/lib/services/grouping.ts:69` 的 `STRATEGY_WEIGHTS`（顺序 `skill_cover / weak_tie / balance / history_avoid`）：

| 策略 | skill_cover | weak_tie | balance | history_avoid |
|---|---|---|---|---|
| `skill_first`（方案A · 能力互补优先（推荐）） | 1.5 | 0.6 | 1.2 | 1.0 |
| `weaktie_first`（方案B · 弱连接优先） | 1.0 | 1.6 | 1.0 | 0.8 |
| `fairness_first`（方案C · 公平优先） | 1.0 | 0.6 | 1.8 | 1.2 |

**打分本身不在 Web 侧**：`previewMove`/`applyMove`/`resetPlan` 都经 `scoreGroups`(`:418`) 调 `POST /internal/grouping/score` 拿 `total_after`/`deltas`/四维 `scores`，Web 只做**违规复核**与 `totalScore` 落库。唯一本地计算是 `localViolations`(:112) 复核 H2（禁止同组），合并策略为 `{ ...local, ...fromAlgo.filter(v => v.code !== 'H2') }` —— **H2 只信本地，H1/H4/H5 信 algo**，理由是注释所述"防止 algo 静默未应用移动仍报旧违规"。

Web 侧真正本地算的是**三方案快照的伪造**：`buildPlanSnapshots`(:331) —— A 原样；B 相邻组（0-1、2-3…）尾部互换；C 每组 shift 一人推到下一组（末组回绕 0）。这些快照**没有经过 algo 评分**，仅用于 `getLatestRun` 的 `groups` 空值自愈与 `originalGroups` 回填。

### 6.3 贡献归因

**不落点估值**：`computeGroupContributions` 只把 algo 返回的 `low`/`high` 写入 `lowPct`/`highPct`，中间值 `point` **被丢弃**（注释："系统只存区间，永不存点估价（铁律）"）。这是 schema 层面刻意为之（`contribution_snapshots` 只有 `lowPct`/`highPct`/`peerMedian`，无 `pointPct`）。

Web 侧自算的两个量：

- 中文口径字数：`artifacts.ts:21` `wordCount(text) = text.replace(/\s+/gu, '').length`（去所有空白后的字符数）。
- 去重哈希：`artifacts.ts:25` `hashContent` = sha256 hex `slice(0, 16)`，用于段落变更判定（16 hex = 64 bit，生日碰撞门槛约 2^32 段，工程上够用）。
- 按期口径（`:47` 内）：`const onTime = !task.dueAt || task.completedAt == null || task.completedAt <= task.dueAt;` —— **无截止日、或从未完成，都算"按期"**。
- 返工口径：`e.toStatus === 'doing' && e.fromStatus === 'reviewing'`。
- 协作产出：修订者≠原作者时计**半权**（`wordsRevised`）。
- `delayCount = Math.max(0, leadTotal - leadOnTime)`。
- 证据权重**正确读课程设置**（`contributions.ts:207-210`）：`w_artifact: settings ? Number(settings.wArtifact) : 0.5`、`w_process: ... 0.3`、`w_peer: ... 0.2`、`fair_share_threshold: settings ? Number(settings.fairShareThreshold) : 0.14`（`settings` 缺失时才回落默认值）。这是全层唯一把 `course_settings` 权重真正接进算法的地方。

### 6.4 同伴互评去极值中位数

`web/lib/services/peer-reviews.ts:226` `roundResults`：

- 单个被评人的样本 = 每份 review 的**维度均值** `avg = Σscores / dims.length`；
- `scores.length >= 4` 时 `trimmed = s.slice(1, -1)`（排序后**去掉最高、最低各一个**），再取中位数；
- `< 4` 时直接中位数（`_median`，偶数取中位两数均值）；
- 排名：按 median 降序，`rank = index + 1`（**不处理并列**，同分不同名次）；
- 输出 `median: Math.round(median * 100) / 100`。

`roundProgress`（`:197`）：应提交数 `expected += n * Math.max(n - 1, 0)`（每组 n×(n−1)），`submitted = count(peer_reviews where roundId)`。

### 6.5 互评异常检测阈值

`web/lib/services/peer-reviews.ts:288` `detectAnomalies`，四条规则（只提示，不改分）：

| type | 判定 | severity |
|---|---|---|
| `mutual_inflation` | A→B 与 B→A 的均值**双方均 ≥ 4.5**，且两人对"其他成员"的评分均值**均 ≤ 3.5**（无其他评分时 `othersAvg` 回落 5，即不算异常） | `high` |
| `extreme_low` | 组内对某人的中位数 − 该份评分 **≥ 2**，且 `!r.comment`（未写评语） | `medium` |
| `single_source` | 某人只收到 **1** 份评价 | `low` |
| `non_response` | `progress.submitted < progress.expected`，课程级只报一条（`break`） | `low` |

### 6.6 重规划的负载与代价公式

`web/lib/services/replan.ts`：

- 负载率 `loadRatio = Math.min(openHours / 42, 1)`（`:90`）—— **常量 42 = 一周可投入工时**，硬编码，未随课程/学期配置。
- `openHours` = 该成员所有 `raci='lead'` 且未 `done`/`cancelled` 任务的 `estHours` 之和（`skills` 字段恒为空对象 `{}`，`MemberLoad.skills` 从未填充）。
- 交付物可砍性 `TYPE_WEIGHT`（`:31`，越低越可砍）：`slide 0.2 / figure 0.4 / table 0.5 / document 0.7 / dataset 0.8 / code 0.9`；`scope_cut` 方案只收 `w <= 0.5`（即 slide/figure/table）。
- 方案A 拆分：`half = estHours / 2`，按 `loadRatio` 升序取**最空的 2 人**，分别给"前半/后半"，每人 `hours = Math.round(half * 10) / 10`。
- 预估影响：方案A `redistribute.length ? 0.5 : 0`；方案B `scopeCut.length ? 1 : 0`；方案C 固定 `2`。
- 触发阈值硬编码 `delayTriggerDays: 2`、`idleTriggerDays: 3`（`:135`，见 §4.11）。

### 6.7 课程设置的服务层校验公式

`web/lib/services/courses.ts:133` `updateCourseSettings`：

- 三类证据权重合计：`Math.abs(total - 1) > 0.011` → `EvidenceWeightError('三类证据权重合计必须为 1.0，当前为 ${total.toFixed(2)}')`（容差 1.1%，对应 `numeric(3,2)` 的两位小数累加误差）。
- 组规模一致性：`min_group_size > max_group_size` → 抛错（复用 `EvidenceWeightError`，语义不符）。
- 注意：**课程级 `course_settings` 的四目标权重（wSkillCover 等，0–2）在此不被归一化校验**，只有三类证据权重（0–1）被要求合计 1.0。

## 7. 值得注意的问题

按严重度排序。所有条目均已在源码中核实。

### 7.1 正确性缺陷（业务结果错）

**① `detectConflicts` 的"依赖冲突"完全没有查依赖图。**
`web/lib/services/conflicts.ts:59-62`：

```ts
const downstream = taskRows.filter(
  (other) => other.id !== t.id && other.status !== 'done'
);
```

`conflicts.ts` 的 import 里**没有 `taskDeps`**（`conflicts.ts:3-9` 只有 `conflictAttributions/conflictResolutions/conflicts/groups/tasks`）。因此任何一个延期或 blocked 的任务，都会把**组内所有未完成的其他任务**算成"下游"，生成的标题 `「X」延期，波及 N 个下游任务` 与 `summary` 里的"组内 N 个未完成任务可能受影响"数字是错的（N = 全组未完成任务数 − 1，与 DAG 无关）。文件头注释（`:26`）写的"任务 blocked/延期且存在未完成下游"在实现中不成立。
附带：`other.status !== 'done'` 未排除 `cancelled`，已砍任务也被计为下游。

**② 健康度"过载/阻塞"输入缺依赖边。**
`web/lib/services/health.ts:26` `loadGroupTasks` 把 `deps: [] as string[]` **硬编码为空**，注释称"由调用方补（health 只需 blocked/overload 判定）"，但唯一调用方 `computeGroupHealth`(:98) **也没有补**。结果：算法侧永远看不到依赖关系，`blocked_score` 只能靠 `tasks.status === 'blocked'` 这类表层信号，无法识别"前置未完成导致的隐式阻塞"。

**③ `loadLastSignals` 跨组污染 + 信号源单一。**
`health.ts:60-69`：`select userId, max(observedAt) from progress_signals where userId in (...) group by userId` —— **只按 userId 聚合，没有 `groupId` 条件**。一个学生在多个课程/小组的信号会被合并取 max，导致"最后活跃时间"永远显得很新，`idle` 维度低估。
更根本的是：`progress_signals` 在真实流程中**只有一个写入点** —— `tasks.ts:439`（`signalType: 'status_changed'`）。`recordSignal`（`health.ts:78`）在全仓**没有任何调用者**（`grep` 仅命中定义处），因此 `checkin` / `idle_detected` / `deliverable_submitted` / `comment` / `peer_helped` 五种 signalType 从不产生数据；`health` 的 `idle_members` 判定实际只由任务状态变更驱动。

**④ `getGroupHealth` 的"最近 30 条"取的是最早 30 条。**
`health.ts:146-151`：`orderBy(asc(snapshotAt)).limit(30)` → 历史曲线拿到的是**课程刚开始时的 30 条**，之后永远不再更新。应为 `desc` 后再 `reverse()`，或 `desc + limit` 后前端反转。

**⑤ `lockGroupSnapshots` 会锁到别组的账本。**
`contributions.ts:474-478`：

```ts
const snaps = await db.select({ id: contributionSnapshots.id })
  .from(contributionSnapshots)
  .where(eq(contributionSnapshots.snapshotAt, latest[0].snapshotAt));
```

**缺少 `eq(contributionSnapshots.groupId, groupId)`**。`snapshotAt` 是全库共享时间戳（批算时同一 `new Date()` 可能被多组复用），会跨组锁定。同时该查询无 `groupId` 前缀索引可用（唯一索引是 `(groupId,userId,snapshotAt)`），退化为全表扫描。

**⑥ "锁"只是布尔标记，不是并发控制。**
`contributions.ts:464` 的 `lockGroupSnapshots` 只写 `attribution_reviews.isLocked = true`，且 `update ... where snapshotId in (...)` **只命中已存在 review 行**的 snapshot —— 没有 review 记录的成员永远不会被锁，`reviewSnapshot` 也不检查 `isLocked`。全仓（`web/lib`）`FOR UPDATE` / `.forUpdate()` 出现 **0 次**，`db.transaction` 仅 10 处（`classes.ts:117`、`contributions.ts:220`、`artifacts.ts:45`、`enrollments.ts:24`、`grouping.ts:579`、`grouping.ts:716`、`replan.ts:166`、`replan.ts:413`、`courses.ts:35`、`tasks.ts:119`）。因此"锁定后不可改分"在并发下不成立。

**⑦ 三处写操作缺事务边界。**
- `tasks.ts:407` `changeTaskStatus`：`update tasks` + `insert task_status_events` + `insert progress_signals` 三写**无事务**，中途失败会留下"状态已变但无事件/无信号"的账本。
- `artifacts.ts:279` `compileFinal`：新建 artifacts + 新建 version 两步**无事务**，失败会留下无版本的空终稿。
- `conflicts.ts:118`/`:174`：`insert attributions/resolutions` + `update conflicts` 均**无事务**。

**⑧ `onConflictDoNothing` 在三张无唯一约束的表上无效。**
- `tasks.ts:311` `addDep` → `task_deps` **无唯一约束** ⇒ 重复边可插入（DAG 边重复会让 `markCriticalPath` 的入参膨胀）。
- `tasks.ts:551` `acceptContract` → `contract_acceptances` **无主键、无唯一约束** ⇒ 同一人重复签署产生重复行，"是否全部签署"的判定会失真。
- 反向对照：`peer-reviews.ts:188` 的 `onConflictDoUpdate` 命中 `peer_reviews_uniq`，是正确用法。

**⑨ `group_members_active_uniq` 未真正防止重复入组。**
唯一索引列为 `(groupId, userId, leftAt)`，Postgres 认为 NULL 互不相等，因此 `leftAt IS NULL` 的行可以重复插入多个 —— 同一人在同一组可有多条在册记录，会污染 `groupMemberIds`、`listGroups`、`roundProgress` 等所有"在册成员"统计。

**⑩ `rejectEvent` 无状态守卫。**
`replan.ts:458`：已 `adopted` 的事件仍可被改为 `rejected`，且不校验 `reason` 非空（注释说"必须填理由"）。

**⑪ `replan` 触发阈值硬编码，与 `course_settings` 脱钩。**
`replan.ts:135`：`const settings = { delayTriggerDays: 2, idleTriggerDays: 3 };` —— `course_settings.delayTriggerDays`(default 2)/`idleTriggerDays`(default 3) 两列**在服务层从未被读取**（另有 `void settings.idleTriggerDays;` 消警告）。教师改了设置也不会生效。

**⑫ 归因入参有两个恒定量，会结构性压低两个维度。**
`contributions.ts:196-206` 传给 algo 的 `members[]` 中：`help_count: 0` **硬编码为 0**（"主动补位"这一 comp 维永远无输入，而 `member_profiles.helpCount` 列存在且从不被读），`cp_total: cpTaskIds.length` 取的是**全组**关键路径任务数 —— 对每个成员都是同一个分母，`cp_done / cp_total` 实际度量的是"全组完成度"而非"该成员的按时率"，`lead_on_time / lead_total` 与它存在口径重叠。
（对照：三类证据权重与 `fair_share_threshold` 是正确的，见 §6.3。）

### 7.4 类型安全与工程卫生

- `any` 全仓 `web/lib` 仅 **1 处**：`web/lib/auth/middleware.ts:9` 的 `[key: string]: any`（`ActionState` 索引签名）。`grouping.ts`/`tasks.ts`/`peer-reviews.ts` 大量 `Record<string, unknown>` 与 `as` 断言（如 `replan.ts:414` `(option.payload ?? ### 7.5 安全与合规

- `algo/client.ts` 的 `ALGO_SHARED_SECRET` 默认 `''`：未配环境变量时**静默退化为无鉴权**，不报错、不告警。

## 8. 结论

**做得好的部分**

1. **建模密度高且对齐规格**：50 张表覆盖身份/画像/分组/任务/契约/溯源/归因/健康/冲突/重规划/互评/通知 12 个域，注释普遍带规格书条款号，表级红线（角色课程级、只存区间不存点估值、pending 约束不参与求解）在 schema 与 service 双侧一致。
2. **段落级溯源是真做了**：`saveVersion` 的四规则 diff（`create`/沿用/`revise` 保留原作者/`delete`）是这套系统里最扎实的一段实现，配合 `getSnapshotEvidence` 的三路证据下钻，确实能"从百分比追到某句话是谁写的"。
3. **降级策略选点准确**：7 个 algo 端点中只有 2 个 LLM 端点做降级，5 个纯算法端点直接抛错 —— 避免了"算法失败却给出看似正常的错结果"。
4. **避免 N+1 的意识存在**（`listClasses` 三查询合并），`peer_reviews_uniq` 的 upsert 用得正确。

**主要风险**

1. **冲突检测的依赖冲突判据缺失**（§7.1①）—— 这是产品核心功能之一，当前输出在语义上是错的。
2. **健康度输入链断裂**（§7.1②③④）—— 依赖边恒空 + 信号只来自状态变更 + 历史取最早 30 条，导致"健康度"这个卖点在实际数据上不可信。
3. **并发控制实际不存在**（§7.1⑥）—— 全仓零 `FOR UPDATE`、10 处事务且均不覆盖"读-判-写"全链，`selectPlan`/`lockGroupSnapshots`/`computeGroupContributions` 在多人同时操作时会互相覆盖。
4. **画像证据链（`member_profiles`/`member_skills`/`milestones`）在产品流程中为空**（§7.3）—— 分组算法里的 `skill_cover` 维度实际只能依赖 `skill_cards`，与"历史协作倾向"相关的维度全部悬空。
5. **配置项与实现部分脱钩**（§7.1⑪⑫）—— `course_settings` 的重规划触发阈值（`delayTriggerDays`/`idleTriggerDays`）服务层从未读取（`replan.ts:135` 硬编码 2/3）；归因的 `help_count` 与 `cp_total` 也不是按成员计算。三类证据权重倒是接对了。
