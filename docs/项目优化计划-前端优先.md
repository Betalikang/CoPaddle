# CoPaddle 项目优化计划（前端优先）

> 制定日期：2026-11-17。依据：`docs/项目资料整理.md` 与本地代码核对；仅规划，不改业务代码、不重置演示数据、不操作生产服务器。工作区已有大量未提交改动，实施时须先建立基线并保留现有修改。本文工期是单人开发的粗略估算，非已测性能数据。

## 一、目标与边界

**产品主线**：教师完成「建课 → 导入名单/画像 → 生成并选定分组 → 监控预警/复盘」；队长完成「拆解任务 → 分派/契约 → 处理阻塞/重规划 → 汇编交付」；队员完成「认领/更新任务 → 提交痕迹 → 互评/查看贡献区间与申诉」。先保证三条路径**可理解、可恢复、可追溯**，再优化渲染和视觉。现有 25 个页面、75 条 API 路由及 50 张表是源码/资料的当前口径，不把规格书的 52 页面/155 API 当作待补全清单（`docs/项目资料整理.md:189-198`）。

**约束**：不修改贡献归因“只展示/存储区间”的规则；角色始终按课程成员关系而非 `users.role`；不把贪心兜底描述成最优解；不把尚未接线或占位的能力包装成已实现；先用本地数据/脱敏副本验收，绝不以公网上的演示账号和真实口令做自动化测试。

## 二、优先级与实施顺序

排序规则：用户影响与数据误导风险 > 关键路径阻断 > 覆盖面 > 成本。P0 需在继续扩大功能或做视觉重设计前完成；P1 完成主流程与可访问性；P2 做性能和结构治理；服务层纠偏从 P0 同步排期、在相关 UI 承诺放行前完成。每阶段均在独立分支小步提交，不批量重写 20 个客户端页面。

| 阶段 | 建议工期 | 交付结果 | 放行条件 |
|---|---:|---|---|
| P0 正确性与安全门槛 | 3–5 开发日 | 共用请求错误处理、关键操作反馈、权限区分；公网演示风险隔离 | 401/403/5xx/超时不会变成“无数据”或假成功；若现网仍有明文会话或公开默认口令，先停止对外开放并完成修复验收 |
| P1 三端核心流程 | 5–8 开发日 | 教师分组、队长任务、队员交付的任务导向页面；移动导航/键盘可达 | 三种角色在桌面/手机完成脚本任务，遇错能明确恢复 |
| P2 性能、测试与组件治理 | 4–7 开发日 | 页面数据拆分、按需加载重图、自动化回归/性能基线 | 指标基于改前/改后相同数据与设备实测，测试与构建通过 |
| 服务层并行线（P1 前置） | 5–10 开发日，与 P0/P1 并行 | 健康度/分组/重规划口径纠偏、状态机和审计 | UI 展示与权威结果一致；异常路径有回归测试；高风险事项不能等到 P2 后 |

### P0：先阻断安全风险，再修好“看起来成功、其实失败”

**立即处置的独立发布门槛**：资料于 2026-11-17 记录了 HTTP + `COOKIE_SECURE=false` 和演示账号统一密码，但本计划未重新访问服务器，不能把文档实测当作当前线上状态。仓库本地 `deploy/Caddyfile:1-7` 仅监听 `:80`，`web/scripts/seed-digital-image.ts:77` 与 `web/scripts/reset-demo-password.ts:16` 有默认演示口令；更直接的是 `web/app/(login)/login.tsx:13,32-35,135-174` 在登录页展示统一明文口令并支持一键填入。`web/lib/auth/session.ts:53-59` 允许 HTTP cookie，而 `web/middleware.ts:85-100` 在 GET 续期时硬编码 `secure: true`，两处策略在 HTTP 环境下不一致。若生产核验仍存在明文 HTTP 会话或公开默认口令，应先暂停对外展示和真实数据接入，禁用/重置公开演示账号，并将登录页演示入口及口令仅保留于隔离演示构建（正式环境不渲染、不打包口令）；配置域名 TLS、HTTP→HTTPS、统一 Secure cookie 策略，再放行对外使用；该核验与修复**不等待服务层后续治理**。验收：运维提供当前配置的脱敏证据；HTTPS 登录及 GET 续期均保持会话、cookie 带 Secure，默认口令不能登录，正式环境登录页/客户端构建不包含演示账号口令，HTTP 不传送会话。

1. **统一读请求契约**（前端，0.5–1.5 日）。当前多个页面和布局用 `fetch(url).then(res => res.json())`，例如 `web/app/(dashboard)/dashboard/page.tsx:15`、`web/app/(dashboard)/dashboard/courses/[id]/grouping/page.tsx:35`、`web/app/(dashboard)/dashboard/courses/[id]/tasks/page.tsx:70`；HTTP 403/500 的 JSON 会被 SWR 当成成功结果。抽一个带 `status`/安全错误文本的 typed fetcher，非 2xx 抛异常，区分 401（重新登录）、403（无权）、404（不存在）、5xx/网络（重试）；共用稳定的 loading/empty/error/retry 状态，别把 403 渲染为空列表。课程角色闸门 `web/components/course-role-gate.tsx:21-36,101-106` 应对授权错误明确区分，且 API 继续是权限最终裁判。验收：Mock 上述状态码，三个角色的列表和直链均显示正确状态；刷新/重试后不保留旧错误。
2. **关键写操作统一成功判定**（前端，1–2 日）。课程切换 `web/app/(dashboard)/dashboard/page.tsx:50-63` 未核对 `switch-context` 响应就跳转；分组 `grouping/page.tsx:247-259,280-292` 的还原/重新求解也无成功判定，`grouping/page.tsx:197-220` 在 apply 确认之前就显示 preview 得分。统一服务端结果为唯一已保存状态；预览标“未保存”，失败时回滚/刷新，禁止错误响应后假跳转；解散行为先核对所选目标，避免默认指向第一组（`grouping/page.tsx:262-277`）。验收：对每个动作注入 400/409/500、断网/超时与双击，页面不出现假成功、目标组正确、按钮解除 busy 并提供明确重试。现有 `tasks/page.tsx:696-714` 的普通写操作已有错误处理，应复用而非重写。
3. **优先清除误导性业务展示**（前后端联动，1–2 日）。`web/lib/services/health.ts:56-66` 给算法的依赖边为空，且教师总览 `health.ts:181-219` 只读取快照、可能为空或陈旧；`web/lib/services/grouping.ts:153-194` 的历史同组配对为空，仅在旧计划组数据为空的自愈路径（`:333-385`）会构造未经求解和重评分的 B/C 快照；正常新求解三方案并非伪造。先在 UI 标明计算时间/快照来源/降级与不可用，只用权威数据，后端根因修复须同步启动、不能拖至 P3 后才开始。验收：无数据/陈旧/降级态可辨，正常与异常自愈方案评分逐项对账。

### P1：把能力组织成三端任务流

4. **教师工作台**（1.5–2.5 日）。在现有课程概览上突出“名单与技能卡就绪 → 生成方案 → 人工微调 → 选定 → 查看健康与预警”；分组失败/无可行解给出可操作原因（组数、规模、冲突约束），区别“方案未生成”“求解中”“贪心降级”“已选定”。保留现有三方案 Tab、分组分页和鼠标拖动，不重做算法。验收：教师能从未建组课程走到选定方案，错误时不会丢已保存方案。
5. **队长/队员工作台**（2–3 日）。把任务生成/手工调整、契约发布签收、任务状态与依赖、交付物版本、互评/贡献区间串成下一步行动；AI 120 秒等待需持续状态说明，失败落手工入口（见 `docs/项目资料整理.md:294-305`）。`web/app/(dashboard)/dashboard/courses/[id]/tasks/page.tsx:716-749` 的 AI 生成遇网络拒绝/非 JSON 响应缺可见 catch，复用同页 `:696-714` 已有写请求错误处理并保留输入；`web/app/(dashboard)/dashboard/courses/[id]/skill-card/page.tsx:36-57,98-106` 须把读取失败与新卡默认零值分开，读取失败禁用保存；`web/app/(dashboard)/dashboard/courses/[id]/reviews/page.tsx:70-95,179-203` 首轮创建失败也要在零轮次视图显示错误。任务 DAG 优先保证列表和详情可完成操作，再按需使用图；不得改变仅存 `lowPct/highPct` 的归因规则。验收：三种失败注入后可见错误、输入保留、旧数据不被零值覆盖；AI 不可用不阻断手工流程，队长/队员各走通一条真实权限闭环。
6. **移动端与无障碍**（1.5–2.5 日）。移动侧栏当前是条件渲染的遮罩+`aside`（`web/app/(dashboard)/dashboard/layout.tsx:58-76`）；评估用现有 Radix Dialog/Sheet 语义替换，确保焦点移入/返回、Esc 关闭、背景不可操作、清晰标签。分组已有“点选成员 → 移至此处”的非拖拽操作（`grouping/page.tsx:239-245,439-499`），应保留并完善选中与违规结果播报，而不是误报“只能拖拽”。验收：375px/桌面键盘+屏幕阅读器完成导航和分组移动；焦点不落在遮罩后，动态反馈可感知。

### P2：只优化已测瓶颈，不盲目改框架

7. **渲染与请求拆分**（2–3 日）。`tasks/page.tsx` 为约 2,041 行客户端页，组合 ReactFlow、DND、表单和多个 SWR 请求（`web/app/(dashboard)/dashboard/courses/[id]/tasks/page.tsx:1-70,498-550`）；优先拆为独立任务列表、DAG、契约面板，重图表按需加载，避免主流程等候图形包。`web/app/(dashboard)/dashboard/layout.tsx:22-40` 的课程信息请求与子页面请求可共用同一 key/缓存。对可读首屏做**小范围**服务端读取与客户端交互岛试点；不要全站一次迁移，也不要擅自升级 canary 框架。验收：固定 24 组/216 任务的隔离测试数据，记录优化前后的生产构建 JS、LCP/INP/CLS 的第 75 百分位和请求数（同设备同网络），以不回退为门槛并记录实测差值。成绩导出另需修复 `web/app/(dashboard)/dashboard/courses/[id]/grades/page.tsx:186-195` 的可点击 Badge（替换为可键盘操作的按钮/checkbox 并标记选中态）及下载失败反馈（`:145-147`）；验收 Tab/Space 可选列且 403 不打开错误页冒充成功。
8. **测试与发布门禁**（2–3 日）。当前 `web/tests/services/courses.test.ts` 是唯一 web 测试文件，且会连数据库插删数据；`web/vitest.config.ts:8-14` 为 Node 环境，`web/package.json:10-19` 尚无测试脚本。先加无需数据库的 fetcher 测试，再为组件/浏览器交互建立合适环境，覆盖角色闸门、分组失败回滚、移动抽屉、技能卡读取失败与 AI 生成网络异常；教师/队长/队员各有隔离数据的浏览器冒烟。CI 顺序：类型检查 → 离线单测 → 隔离临时库服务测试 → 生产构建 → 三角色冒烟；真实 LLM 测试显式 opt-in，不对线上库运行种子。验收：P0 缺陷先有旧版可复现、新版可通过的测试；构建与三角色主路径全绿。

### 服务层并行线：前端数据正确性的前置依赖

9. **健康度与分组口径**：`web/lib/services/health.ts:56-66` 须补真实任务依赖边，`:71-85` 的用户最后信号须限定在本组/本课程；`:142-219` 须定义快照刷新策略与 `snapshotAt` 新鲜度阈值。教师总览当前只读快照；`web/app/api/groups/[id]/health/route.ts:40-45` 的 GET 仅在无快照时补算，POST 才强制重算，不得按旧资料描述“课程总览触发快照”。分组 `web/lib/services/grouping.ts:153-194` 补历史同组样本，自愈路径 `:333-385` 需校验硬约束、真实重评分或拒绝回填；正常求解返回的三方案不受该伪回填问题影响。验收：跨组信号隔离、未完成前驱触发预警；快照时间与刷新可追溯；三方案各自评分可复算。
10. **状态机、审计与数据完整性**：`web/lib/services/replan.ts:519-527` 缩范围直接写 cancelled，须复用 `web/lib/services/tasks.ts:449-488` 的合法转换并写状态事件/进度信号；冲突去重覆盖 analyzing；`web/lib/services/peer-reviews.ts:76-109` 的 open/close/publish 校验合法前态；归档课程明确只读。重规划采纳/驳回已有 pending 守卫（`replan.ts:489-500,534-556`），不应重复列为缺陷。修复在册成员唯一与任务依赖唯一约束（`web/lib/db/schema.ts:390-405,461-469`）前先清重、迁移并回滚演练。验收：并发/重复点击只产生一次合法转换与可查事件；迁移前后数据量核对，非法状态返回冲突而非乱序更改。
11. **部署与安全的后续治理**：P0 已把“若核验仍为 HTTP + 公开默认口令则停止对外展示”列为独立放行门槛；本项只覆盖长期治理：建立隔离演示环境、修复 `web/middleware.ts:85-100` 的续期 cookie 策略与 `web/lib/auth/session.ts:53-59` 的签发策略不一致，补齐环境与回滚手册。纠正 `db:setup` 与环境示例的遗留说明，迁移失败不得在脚本里被 `|| true` 吞掉（`docs/项目资料整理.md:403-460`）。验收：各环境口令隔离且不使用公开默认值；迁移失败中止发布；HTTPS 下登录和续期会话均有效且带 Secure 属性。

## 三、实施与验收机制

- **第 0 天建立基线**：保留当前未提交改动；在隔离本地环境复现 P0 行为，记录三角色关键流程、状态码、浏览器控制台、截图与网络耗时；不得直接拿资料中的生产计数当作性能基线。
- **任务切分**：P0 当期即写 fetcher、分组失败回滚的复现测试；P2 扩展测试基础设施与全流程覆盖，并非延后 P0 测试。每项只改一个用户流程或共享基础件，先复现、再实现、最后三角色回归；健康度/分组的后端根因必须在相应 UI“实时/准确”承诺恢复前验收。静态代码审查不能证明视觉表现，需对 375px/桌面实机截图和交互逐项验收。
- **发布关卡**：本地单测/构建 → 隔离预发布三角色冒烟（空数据、正常、网络故障、无权、降级）→ 数据备份及迁移演练 → 灰度/监控 → 回滚预案。不能把 200 首页当作业务流程健康证明。
- **建议指标**：关键操作假成功为 0；三角色主路径完成率为 100%（固定冒烟脚本）；P0 状态覆盖率 100%（401/403/404/5xx/断网/重复提交）；移动与键盘关键流程均可完成；性能指标必须先测基线后定改善目标，不编造现有秒数。

## 四、暂不做

不以“补齐 52 个页面/155 个 API”为目标，不先做全站视觉翻新，不先换状态管理框架，不直接在生产跑压测或种子，不在没有真实业务实现时开放组间借调/并组/邮件微信通知。这些均让位于正确性、三角色主路径与可验证交付。
