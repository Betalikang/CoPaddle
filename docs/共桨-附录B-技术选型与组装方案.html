附录 B · 技术选型与组装方案

不从 0 开发：fork 脚手架，装零件，只自建三块 前提：项目仅用于学习，不商用、不对外开放上线。这个前提大幅放松了许可约束，但改变了推荐结论的方向——不是变得更激进，而是变得更务实。

B.1

先厘清一件被普遍误解的事：许可管的是「分发」，不是「使用」

开源许可几乎从不限制你如何使用软件，只限制你如何传播它。理解这条，你手上的选择会瞬间多出一倍。

结论：你现在几乎可以用任何东西

在"仅学习、不商用、不对外开放上线"的前提下，GPL-3.0 的 gruepr 从"只能读思想"升级为"可以直接读代码、抄算法、甚至整体借鉴"。这是这次前提变化带来的最大收益——它恰好是开源世界里唯一一个完整实现了"多目标分组评分函数"的项目。

三个仍然要注意的点

  • 参赛材料的性质是灰色的。提交代码、答辩演示、上传仓库截图——严格说不构成法律意义上的"分发"，但如果评委或观众据此复现，性质会变。安全做法：仓库保持私有，演示用本地或内网环境。
  • 学术诚信要立住。在方案书里明确标注哪些思路来自开源项目（gruepr 的评分函数、CATME 的方法论对标）。主动标注来源是加分项，被评委问出来才扣分。
  • 别让"反正是学习"变成技术债。现在省下的 3 天重构成本，将来要上线时会以 30 天的代价还回来。核心的溯源与归因模块建议从一开始就自己写。
B.2

但推荐结论没变：仍然 fork 脚手架，而不是 fork 教育项目

许可闸门打开之后，唯一还剩下的障碍是工程量与技术栈。这两个障碍反而比许可更硬。

为什么"形态最全"反而不是优势

一个已经做完了产品 A 的项目，你要把它改成产品 B，改动量往往大于在一个干净脚手架上新建——因为你要先理解它、再拆除它、最后重建。而一个只提供地基和通用能力（登录、数据库、UI、权限中间件）的脚手架，不需要你拆除任何东西。这就是"fork 脚手架"与"fork 整机"的本质差别。

B.4

架构：双服务结构

前端用 TypeScript 生态，算法用 Python 生态。中间用一层 HTTP 接口隔离，这样算法可以独立迭代，也不拖慢前端开发。

决策选择与理由
算法为什么独立成服务约束求解器、图算法、LLM 编排的生态都在 Python。硬塞进 Next.js 会失去 ortools 与 networkx 这两个最省力的武器
数据库为什么共享算法服务只读画像数据、只写结果表，不做业务写入。避免双写不一致
为什么不用消息队列课程规模（一个班 30–50 人）下同步 HTTP 足够，分组求解限时 10 秒内。不要为不存在的并发量引入基础设施
AI 编排为何暂不上 LangGraphM3（拆解）与 M4（重规划）都是单轮结构化输出，直接调 API 更快落地。等出现多步工具调用需求再引入
B.5

三块必须自建的模块：实现要点

① 多目标分组（用约束求解器，别手写遗传算法）

很多人第一反应是写遗传算法——不要。CP-SAT 是 Google 的工业级约束求解器，声明式建模、几行代码、能在几秒内给出可证明的最优或近优解，还自带时间上限。手写 GA 你要自己调种群大小、交叉率、变异率，跑出来的解还不如它。

# grouping.py — 约 150 行可跑通核心
from ortools.sat.python import cp_model

def solve_grouping(students, num_groups, cfg, time_limit=10):
    m = cp_model.CpModel()
    x = {(s["id"], g): m.NewBoolVar(f"x_{s['id']}_{g}")
         for s in students for g in range(num_groups)}

    # 硬约束：每人恰好进一个组
    for s in students:
        m.AddExactlyOne(x[s["id"], g] for g in range(num_groups))

    # 硬约束：组规模上下限
    size = {g: sum(x[s["id"], g] for s in students)
            for g in range(num_groups)}
    for g in range(num_groups):
        m.Add(size[g] >= cfg["min_size"])
        m.Add(size[g] <= cfg["max_size"])

    # 硬约束：不可同组配对
    for a, b in cfg["forbidden_pairs"]:
        for g in range(num_groups):
            m.AddAtMostOne([x[a, g], x[b, g]])

    # 软目标：拉平组间实力（最小化最大值与最小值之差）
    power = {s["id"]: sum(s["skills"].values()) for s in students}
    tot = {g: sum(x[s["id"], g] * power[s["id"]] for s in students)
           for g in range(num_groups)}
    hi = m.NewIntVar(0, 10**6, "hi")
    lo = m.NewIntVar(0, 10**6, "lo")
    for g in range(num_groups):
        m.Add(tot[g] <= hi)
        m.Add(tot[g] >= lo)
    m.Minimize(hi - lo)

    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = time_limit
    solver.Solve(m)
    return [[s["id"] for s in students if solver.Value(x[s["id"], g])]
            for g in range(num_groups)]

要把它变成"多目标"，用加权求和即可：把技能覆盖度、弱连接引入度、组间均衡、历史规避四项各自写成线性表达式，按权重合成单一目标。权重就是教师端那几个滑块。这样"拖动组员实时看到得分变化"也容易实现——拿到解后本地重算一次四项得分即可，不需要重新求解。

② LLM 任务拆解（核心是让它输出 DAG，不是让它"给建议"）

关键：用结构化输出约束住格式，让模型返回可编程的数据，而不是一段好看的文字。依赖关系用 id 数组表达，前端据此画图、算关键路径。

// schema.ts — 约束 LLM 的输出结构
const TaskNode = z.object({
  id:          z.string(),
  title:       z.string(),
  deps:        z.array(z.string()),   // 依赖的任务 id → 构成 DAG
  estHours:    z.number(),
  skills:      z.array(z.string()),   // 所需技能 → 与成员画像做匹配
  deliverable: z.string(),            // 交付物形态 → 后续溯源用
  milestone:   z.string(),
});

const Plan = z.object({
  tasks: z.array(TaskNode),
  contract: z.object({                // 协作契约：冲突的根治手段
    glossary:   z.array(z.object({ term: z.string(), definition: z.string() })),
    interfaces: z.array(z.string()),
    format:     z.string(),
  }),
});

提示词里必须交代的三件事：一是任务的粒度（建议 2–8 小时可完成）；二是必须显式声明依赖，不允许出现孤立任务；三是生成的 contract 要写具体，比如统一"客流量"的口径与单位——把这层写进提示词，事后 80% 的"成果冲突"根本不会发生。

③ 交付物溯源与贡献归因（护城河，必须自己写）

做法是"组装式交付"：成员在系统内撰写自己的部分，由系统汇编成终稿，而不是大家传附件。这样段落归属天然可查。

-- 核心表：段落级归属是溯源的根基
artifact_segments (
  id, artifact_id, segment_index,
  author_id,            -- 谁写的这段（由撰写记录产生，非自报）
  kind,                 -- paragraph / figure / table / code
  edited_by,            -- 谁后来改过 → 可算返工与审阅
  created_at, updated_at
)

归因时把三类证据加权汇总：

  • 产出物证据：段落级归属统计 → 主责产出占比、协作产出占比
  • 过程证据：主责任务完成数、按期率、关键路径延期次数、返工轮次、主动补位次数
  • 同伴证据：组内互评（去极值后取中位）+ 队长评语

输出贡献构成 + 区间估计 + 置信度 + 可下钻证据，不输出单一分数。"不输出分数"不是保守，而是唯一能规避 AI 判分争议的设计。

搭便车预警阈值可以直接引用文献

有实证研究给出：当最不活跃成员的贡献低于其应分担份额的 14% 时，团队大概率会感知到贡献不均。把这个 14% 做成系统阈值，答辩时可以说"阈值不是我们拍的，来自一篇实证研究"。同时该研究还发现贡献不均与团队成绩没有稳定关联——这正好是"只给证据、由教师判断"的依据。

B.7

实施路径：按"能演示"倒推排序

顺序不是按模块重要性排，而是按"哪一步做完就能演示、就能拿分"排。每一步结束都是一个可展示的节点。

阶段目标产出与验收标准
P1 跑通骨架与三角色 fork 脚手架并启动；数据模型改造为课程/班级/小组/成员；三种角色登录后看到不同界面。
验收：用教师账号能建课并导入名单
P2 拿下分组（第一个亮点） FastAPI 算法服务 + CP-SAT 分组；教师看到三套方案与解释；拖动组员实时显示四项得分增减。
验收：现场拖动，曲线实时变化——这是答辩的第一个杀手锏
P3 任务拆解与看板 上传作业要求 → LLM 输出任务 DAG + 协作契约 → 自动分配到人；前端看板 + 甘特。
验收：任意一份作业 PDF 能在 30 秒内拆成带依赖的任务树
P4 进度感知与重规划 看板状态变更自动沉淀为进度信号；关键路径滞后触发预警；生成三个重规划方案及代价说明。
验收：手动把一个关键任务标为延期，系统弹出波及评估与补救方案
P5 贡献归因账本（第二个亮点） 平台内撰写产出段落并汇编；生成贡献构成 + 区间 + 置信度；任一条结论可下钻到原始证据。
验收：从结论一路点回到段落级撰写记录——这是答辩的第二个杀手锏
P6 互评、终审与打磨 同伴互评表单；教师终审与调分界面；演示数据构造；录屏与截图。
验收：完整走通一遍六步演示脚本不掉链子

P2 和 P5 是两个必须做扎实的节点

P2 的"拖动组员实时看到目标函数变化"和 P5 的"贡献结论下钻到原始证据"，是把抽象的"AI 规划"与"AI 归因"变成评委能亲眼看到的东西。其余部分做得普通没关系，这两处做好了就能拉开差距。

B.8

时间不够时的降级方案

如果只剩很短时间，砍掉哪一块、保住哪一块，需要有明确的取舍规则。

模块降级策略说明
分组算法 可降级 不上 CP-SAT，直接手写"贪心 + 局部交换"。甚至可以先只优化"组间实力均衡"这一个目标，只要拖动时得分能实时变化，演示效果就成立
任务拆解 不要砍 这是 AI 含量最直观的部分，一个 API 调用加一个 schema 就能出效果，性价比最高
进度采集 可降级 不做自动信号沉淀，改成"成员在看板上手动更新状态"。演示时看不出差别
重规划 可降级 不生成三个方案，只生成一个推荐方案 + 代价说明
交付物溯源 可降级 不做真实的版本 diff，改成"提交时由系统引导标注段落归属"。产品概念完全不变，只是实现变薄
同伴互评 可降级 简化成一个 5 维打分表单，不做防作弊与异常检测
拖拽分组可视化 必须保 这是现场演示最出效果的一处，砍了等于砍掉一半答辩表现力
证据下钻 必须保 哪怕只有一条结论能点开看到证据，也要保住。它证明"可解释"不是口号
