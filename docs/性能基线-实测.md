## 1. 固定隔离数据（计划第 7 项要求的口径）

脚本 `web/scripts/perf-fixture.ts` 一次性生成，**24 组 × 8 人 = 192 名学生**（低于 `MAX_STUDENTS_FOR_CPSAT=200`，走真实 CP-SAT 求解而非贪心兜底），每组 9 个任务（8 条依赖链边）：

```
已落库小组数=24 方案组数=24
{"RUN":"0287b87a","courseId":17,"groupId":94,"groups":24,"tasks":216,"deps":192,...}
```

复测方式：

```powershell
# 1. 造数据（指向隔离库，别对生产库跑）
$env:POSTGRES_URL='postgresql://postgres@127.0.0.1:5433/copaddle'
$env:ALGO_SERVICE_URL='http://127.0.0.1:8010'
npx tsx scripts/perf-fixture.ts        # 输出 courseId 与 teacher/captain 两枚 cookie

# 2. 量指标
node scripts/perf-measure.mjs <courseId> <teacherCookie> <captainCookie>
# 3. 量无障碍与 375px
node scripts/a11y-check.mjs <courseId> <teacherCookie> <captainCookie>
```

两个脚本都用 `scripts/lib/playwright.mjs` 解析 Playwright；本机没有把它装进项目依赖，需要 `PERF_PLAYWRIGHT_PATH="file:///.../node_modules/playwright/index.js"`（Windows 中文用户名下裸模块解析拿到的 `chromium` 是 undefined）。`a11y-check.mjs` 全部 PASS 时退出码 0、有 FAIL 时退出码 1，可直接进 CI。

**两个必须注意的坑（都会让指标看起来「变好」而实际没测到东西）**：

1. **cookie 前缀**：`perf-fixture.ts` 打印的是完整 Cookie 头 `session=<jwt>`，而 Playwright `addCookies` 需要的是 value 本身。直接传进去会存成 `session=session=<jwt>`，服务端解不出 token，所有页面回落登录页——实测表现为「每页 16 个请求、LCP 120ms、JS 161.1KB」，全是登录页的数字。现在两个脚本都用 `normalizeSessionCookie()` 去前缀，并在跑指标前先 `GET /api/user` 断言 200，否则直接退出码 2。
2. **AUTH_SECRET 必须一致**：`perf-fixture.ts` 与服务端要用同一个 `AUTH_SECRET`，否则 fixture 签出来的 JWT 服务端验不过（同样退化成登录页）。本机复现时是先 `$env:AUTH_SECRET` 从 `web/.env` 读出来再起 `next start`。

要点：

- **LCP 108–372ms**，全部远低于 Good 阈值 2500ms；最慢是 375px 的分组工作台（372ms，24 组 × 8 人的成员卡片 + 雷达图同时首屏渲染）。
- **CLS 0–0.0446**，全部低于 Good 阈值 0.1；唯一超过 0.01 的是桌面 192 人名单表（表体定型 0.0446）、账号设置页（0.0292）与课程首页（0.015），均非跳变式数值。
- **longtask 本次全部 0**（上一轮桌面分组工作台出现过 1 条 52ms，属抖动范围）。
- **横向溢出全部为 0**（`documentElement.scrollWidth === innerWidth`）。
- **JS 传输量 161–329KB**，其中分组工作台最高（326.9KB，含 recharts）；登录页最低（161.1KB）。
- CSS 传输字节为 0 是测量口径导致的：Next 15 把样式以 `<link rel=stylesheet>` 预载并在导航阶段计入，`PerformanceResourceTiming` 里没有单独的 CSS 条目。

### 交互延迟（INP 近似：Event Timing API 的 interaction duration）

| 页面 | 交互 | 样本 | max(ms) | p75(ms) |
|---|---:|---:|---:|---:|
| 分组工作台（点选成员 chip ×2、切方案 Tab ×2） | 4 | 12 | 24 | 24 |
| 任务与依赖（队长，清单↔看板切换） | 2 | 6 | 64 | 64 |

INP 判定阈值为 200ms（Good），两组交互均在 Good 区间内。采样用 `durationThreshold: 16` 的 `PerformanceObserver({ type: 'event' })`，只统计 `interactionId` 非空的真实交互。

### 第 75 百分位汇总（计划第 7 项要求的口径）

计划要求记录「LCP/INP/CLS 的第 75 百分位」。单次首屏测量只有一个样本，这里的 p75 是**跨页面**取 8 个页面样本的 75 百分位（每个视口分别算），代表「用户在任取一页时最可能遇到的值」：

| 指标 | 375px p75 | 1280px p75 | 阈值(Good) |
|---|---:|---:|---:|
| LCP | 312ms | 240ms | ≤2500ms |
| CLS | 0 | 0.015 | ≤0.1 |
| INP（交互延迟近似） | 24ms | — | ≤200ms |

要得到真实用户的 p75（含网络抖动与设备差异），需要在真实流量上跑 `web-vitals` 上报，本机无法产出；本表只能作为**同设备同网络的回归基准**，用来判断后续改动是否回退。

## 3. reactflow 按需加载的实测差值（唯一可给出改前/改后差值的项）

任务页把 DAG 画布改为 `next/dynamic(() => import('./task-dag'), { ssr: false })`，实测同一页面同一会话：

| 阶段 | 请求数 | JS(KB) | reactflow 资源 | DAG 已渲染 |
|---|---:|---:|---:|---|
| 教师未选组（无计划） | 67 | 250.9 | 0 | 否 |
| 选组后（DAG 出现） | 72 | 300.3 | 2（`4ad41dfc6a7cd604.js` + `34f7a480985f790d.css`） | 是 |

**差值：reactflow 及其样式共 49.4KB（传输量）只在真正渲染 DAG 时下载**；源码体积上该 chunk 为 137.3KB、样式 6.99KB，均不在任务页首屏的 client-reference-manifest 中。
