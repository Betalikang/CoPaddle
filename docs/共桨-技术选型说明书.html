T1

五条决策原则

选型不是在挑最好的技术，是在挑最不容易出错的技术。这五条决定了后面所有取舍。

#原则具体含义与后果
01 跟着基座走，不跟喜好走 已经决定 fork nextjs/saas-starter（MIT，16.1k star），那么它用什么就用什么。不为了个人偏好把 Drizzle 换成 Prisma——替换成本远大于收益，而且会失去基座后续的更新能力
02 只有两个运行时 Node 管业务，Python 管算法。除此之外不加第三个语言、不加第三个服务。每多一个运行时，部署、调试、联调的成本都要翻，而收益往往只是"写法更优雅"
03 能力向下取，不向上要 能用数据库解决的问题不用中间件，能用规则解决的问题不用模型，能用标准库解决的问题不用依赖。全文 12 条「明确不用」是这条原则的具体产物
04 许可先看，能力后看 同为可选时，优先选 MIT / Apache-2.0。这一条直接改掉了两个决策：PDF 解析从 pymupdf（AGPL）换成 pdfplumber（MIT）；分组算法宁可自己写也不引入 gruepr（GPL-3.0）的代码
05 每个选择都要能讲出否决理由 说不清"为什么不选另一个"的选择，通常意味着其实没想清楚。本文档每一项都强制填写备选与否决理由。答辩现场被问「为什么不用 XX」，这就是现成的答案
T2

前端选型

52 个页面、4 个端次、需要三种专业图形。前端是整个项目工作量最大的部分（60 人天），所以每一项都优先选"少写代码"的方案。

项选定备选否决理由

状态管理

分两层，不要混用

服务端状态（接口数据）用 TanStack Query——缓存、失效、重试、乐观更新它全包了。客户端状态（当前课程上下文、拖拽中的临时状态、面板开合）用 Zustand。
最常见的错误是把接口数据也塞进 Zustand，然后手写缓存失效逻辑——那是重造一个更差的 Query。这条分界线一开始就划清，后面能省大量时间。

用途选定备选否决理由

项选定备选否决理由
表单react-hook-form受控组件手写 / Formik 技能卡、约束设置、契约编辑、互评表单都是多字段表单。手写受控状态会写出大量样板；Formik 性能与维护活跃度均不如前者

拖拽（分组工作台的核心）

项选定备选否决理由
拖拽库dnd-kitreact-beautiful-dnd react-beautiful-dnd 已停止维护（作者转向商业产品），且官方仅支持 React 18 以下。dnd-kit 活跃维护、支持 React 19、内置键盘拖拽与屏幕阅读器支持——后者正好满足规格书里"必须提供键盘替代路径"的无障碍要求

一个提前定好的实现约定

分组工作台的拖动不在拖动过程中请求接口，而是：拖动中本地做初步校验并即时反馈 → 松手后调用一次 preview-move → 拿到服务端权威结果后再更新面板。
这样既保证操作跟手，又保证得分数据以服务端为准。本地校验只用于给即时反馈，不作为最终判定。

后端选型（应用层）

应用层寄生在 Next.js 里，不额外起服务。这是"只有两个运行时"原则的直接体现。

项选定备选否决理由
接口层Next.js Route Handlers
+ Server Actions		 独立的 NestJS / Express 服务 独立后端要多维护一个进程、一套鉴权中间件、一份类型定义，还要处理跨域。在只有两个运行时的约束下，这是纯粹的额外成本。Server Actions 处理表单提交尤其省代码
ORMDrizzle ORM Prisma 基座已集成 Drizzle。换 Prisma 意味着重写 schema、重做迁移历史、改掉所有查询。此外 Drizzle 更接近 SQL，写复杂聚合（贡献矩阵的多人统计）时更灵活，也不会有 Prisma 客户端那层运行时开销
迁移Drizzle Kit 手写 SQL 迁移脚本 47 张表的演进，手写迁移必然会漏字段、漏索引。迁移统一由 Drizzle Kit 管理，Python 侧不参与建表——避免两套迁移互相打架
鉴权jose + HttpOnly CookieNextAuth / Auth.js 基座已自带轻量会话方案。更重要的原因是我们需要完全控制角色逻辑——三种角色、且角色是"课程级"而非全局的（见规格书 S1 的警示），NextAuth 的模型不容易塞进去。自己写反而更简单可控
密码哈希框架内置的 bcrypt/argon2自己实现 这条不需要讨论。任何情况都不要自己实现密码学
权限自建中间件（课程归属 + 小组归属双校验）CASL / Casbin 权限模型很简单（四角色 × 资源归属），两张表的联合查询就能判断。引入权限框架反而要额外学一套 DSL
后台任务APScheduler（放在算法服务里）BullMQ + Redis 为一个 300 人的课程引入 Redis 是过度设计。需要定时的只有三件事：健康度快照、失联检测、重规划触发判定，都在 Python 侧，用 APScheduler 就够了。分组求解 ≤10s，用数据库状态表 grouping_runs.status 就能表达，不需要队列
接口文档OpenAPI（FastAPI 自动生成）+ 手写 REST 说明GraphQL 前端有 52 个页面但接口形态高度规整（列表/详情/动作）。GraphQL 的价值在于"前端自由组合字段"，而我们的字段组合在开发期就确定了，引入它只会增加缓存与鉴权的复杂度
日志pino（结构化 JSON）console.log 需要按请求追踪（尤其是 LLM 调用链路），结构化日志才可检索
T4

算法服务选型

这是整个产品技术含量最高的部分，也是唯一必须用 Python 的理由。约 10 人天，其中 AI 层已完成 4 人天的量。

项选定备选否决理由
Web 框架FastAPI + uvicornFlask / Django REST FastAPI 自带 pydantic 校验与 OpenAPI 文档，异步原生。而 pydantic 恰好是 LLM 结构化输出解析的必需依赖——选它等于顺手拿到了校验层
约束求解OR-Tools CP-SAT手写遗传算法 / PuLP / 模拟退火 这是最值得花时间解释的一个选择。遗传算法要自己调种群大小、交叉率、变异率、迭代次数，且无法保证满足硬约束——可能跑出"两人被分到同一组"的非法解。CP-SAT 是声明式建模：把约束写出来，它保证解合法，还能给出可证明的最优或近优解，自带时间上限。100 行以内能跑通，手写 GA 至少 400 行且效果更差
图算法networkx手写 DFS/BFS 关键路径、环检测、连通分量本身不难，但 networkx 提供现成实现且经过充分测试。不过要注意：templates.py 里的关键路径目前是手写的（约 20 行），因为它是"最长路径"而非 networkx 的默认最短路径，手写反而更直观。两者保留，按场景选用
文本相似度rapidfuzz + jiebadifflib（标准库） 冲突检测的前置筛选用。difflib 零依赖但速度慢、且没有针对中文的优化。这一步的性能直接决定了 LLM 的调用量，值得引入依赖。jieba 用于中文分词后再算相似度，比纯字符级准确
文档解析python-docx + pdfplumberpymupdf 许可驱动的决策。pymupdf 是 AGPL-3.0，速度快、中文提取效果好，但 AGPL 对未来上线是实质限制。pdfplumber（MIT，基于 pdfminer.six）速度慢一些但完全够用。
另一个更实用的建议：优先引导教师上传 DOCX 或直接粘贴文本。教师布置作业绝大多数用 Word，python-docx 处理中文没有任何问题，完全绕开 PDF 的坑
定时任务APScheduler系统 cron + 脚本 APScheduler 与 FastAPI 同进程，能直接复用数据库连接与配置，不用额外维护 crontab
数据库访问psycopg 3 + 手写 SQLSQLAlchemy ORM / 第二套 Drizzle 算法服务只做两件事：读画像与任务数据、写计算结果表。查询数量少且固定，手写 SQL 最直观。引入第二套 ORM 意味着同一张表有两处定义，早晚会不同步
数值计算numpy纯 Python 贡献归因涉及矩阵式的多人多指标计算，numpy 写起来更短也更不容易错
测试pytest + pytest-covunittest 覆盖率要求 ≥ 80%，pytest 的 fixture 机制对"构造 30 人画像数据"这类场景更省事
依赖管理uvvenv + pip / Poetry uv 的解析与安装速度快一个数量级，且同时管理虚拟环境与锁文件。若团队更习惯传统方式，venv + pip + requirements.txt 也完全可以，不影响架构（gongjiang-ai/ 目前就是这样）

T5

数据库与存储

项选定备选否决理由
主数据库PostgreSQL 16MySQL / SQLite / MongoDB 47 张表里有大量 JSONB 字段（画像、得分、贡献构成、AI 原始响应），PostgreSQL 的 JSONB 可索引可查询，MySQL 的 JSON 型远不如它成熟。SQLite 不支持并发写，不适合多用户；MongoDB 处理我们这种强关系型数据（课程→小组→任务→依赖→段落）会很别扭
向量扩展不需要pgvector 这是本产品一个重要的简化点。我们不做检索增强，因为 AI 的两个调用点都是"给定一段文本做理解"，而不是"从大量文档里找相关片段"。画像数据是结构化的，直接查询即可。不引入向量库，少一个组件、少一层不确定性
缓存层不需要Redis 设计容量 500 并发在线、单课程 300 人。PostgreSQL 完全扛得住，且我们的查询都有索引。需要缓存的地方（如班级画像）用 Next.js 的请求级缓存即可。为了"以后可能要"引入 Redis 是最典型的过度设计
对象存储本地磁盘目录
./storage/uploads		MinIO / 阿里云 OSS / S3 学习项目、不对外开放、单机运行。自建 MinIO 要额外维护一个服务与一套 SDK 对接。本地磁盘加一个明确的目录结构就够了。代码里把存储抽象成一个接口，将来要换只改一个实现类
全文检索PostgreSQL 内置全文索引Elasticsearch 需要搜索的只有任务标题、契约术语、通知。ES 是另一个进程、另一套数据同步逻辑。PostgreSQL 的 tsvector 加中文分词插件完全够用，甚至先只做 ILIKE 也够
备份策略pg_dump 每日 + 演示前手动快照流式复制 / PITR 学习项目不需要高可用。但演示前必须手动快照——演示数据是精心构造的，弄丢了要重造一遍

本地磁盘存储的一个必做约束

文件上传必须做三件事：① 真实类型检测（读文件头魔数，不能只看扩展名）；② 限制大小 ≤ 20MB；③ 存储路径不使用用户提供的文件名，而是用 uuid 加原扩展名，并把原名存在数据库里。第三条是防路径穿越的最低成本做法。

T6

AI 与模型

规格书 S6 已定「只用大模型做两件事」。这里只回答一件事：用哪个模型、怎么调。

模型选择

项选定备选否决理由
主力模型DeepSeek
（deepseek-chat）		GPT-4o-mini / Qwen / GLM 三个理由：① 中文理解强——我们的输入是中文作业要求，输出是中文任务名与契约术语；② 便宜——一学期 100 次调用成本可忽略；③ 已有可用 key。GPT-4o-mini 中文略弱且需外网；Qwen / GLM 也很好，可作为备用

参数temperature = 0.2
timeout = 90s		默认值 / 高温度 拆解类任务要求结构稳定，温度必须压低。高温度会让同一个作业要求两次拆出完全不同的任务图，这在教学场景是不可接受的

重试策略失败重试 1 次 → 失败则降级指数退避多次重试 这是"辅助功能"而非"核心链路"。重试 3 次让用户等 4 分钟，不如第 2 次失败就告诉他"AI 暂不可用，可手工创建"。用户的时间比模型的成功率更重要

关于本地部署大模型：明确不建议

本机有 RTX 4070 Laptop（8GB 显存），确实能跑本地模型——但这个项目不该跑。四个理由：

  • 质量差距明显。8GB 显存只能跑 7B 级别的量化模型，做"把中文作业要求拆成带依赖的任务图"这类复杂结构化任务，输出质量与 API 模型差距很大，而任务拆解恰恰是产品的核心演示点。
  • 成本不成立。一学期约 100 次调用，总 token 量在 10 万级，API 成本可以忽略。省下的钱远小于搭一套 Ollama + 模型管理的时间。
  • 增加部署复杂度。本来两个运行时（Node + Python）就够，本地推理要再加 Ollama 服务、模型文件管理、显存占用与前端开发的资源竞争。
  • 演示风险。答辩现场如果本地服务起不来或显存被占，演示直接卡住。API 调用的失败概率低得多，且有降级路径。

结论：显卡留着跑别的，AI 部分直接调 API。这个判断在答辩时也可以讲——它体现的是"按需选型"而不是"有资源就用"。

项目估算
单次作业拆解输入 3–5k tokens，输出 2–3k tokens

为什么队员端不要一开始就做微信小程序

小程序发布需要企业主体资质。个人主体小程序在教育类目下有功能限制（无法使用部分需要资质的接口），且正式发布需要主体认证与类目审核。一个用于学习和参赛的项目，卡在资质环节上会白耗很多时间。

更关键的是：即使注册成功，你也无法把小程序分享给全班同学使用（需要审核通过并发布），而 H5 只要内网可达就能用。

建议路径：① 先做响应式 H5，用手机浏览器即可完整走通队员端流程；② 如果答辩现场需要"扫一扫"的演示效果，用一个二维码指向内网 H5 地址即可；③ 只有在明确要对外上线时才引入小程序。产品形态不受影响，省下的时间可以投入到分组工作台和贡献账本这两个真正的加分点上。

明确不用的技术（12 条）

这一节和上面的选型同样重要。「不做什么」决定了项目能不能按期完成。每一条都给出不适用的具体理由，而不是笼统的"没必要"。

#不用具体理由
01LangChain / LangGraph 全项目只有 2 个 LLM 调用点，都是"单轮请求 + 结构化输出"。框架解决的是多轮编排、链式调用、状态管理、工具选择——这些问题我们一个都没有。引入它意味着多一层抽象、多一份版本升级风险、多一个调试盲区，换来的是"代码看起来更规范"。直接用 SDK 的代码是 60 行，包一层框架变成 200 行加一份文档
02向量数据库 / RAG 两个调用点的输入都是"一段确定的文本"（作业要求原文、两段产出对比），不需要从知识库里检索。画像数据是结构化的，直接查表。RAG 解决的是"上下文放不下"和"需要外部知识"，我们两个问题都不存在
03多智能体（Agent）框架 产品里没有"让 AI 自主决定下一步做什么"的场景。所有流程都是确定性的：上传 → 拆解 → 展示 → 人工确认。让 AI 自主规划只会引入不可预测性，而教学场景最不需要的就是不可预测。（值得一提的是：共桨本身的功能是"给人类小组装一套调度层"，这和 Agent 框架解决的问题方向相反）
04Redis 设计容量 500 并发在线。PostgreSQL 加索引完全扛得住，所有查询都有明确的索引设计。缓存只用于"读多写少且计算昂贵"的场景，我们最贵的一次计算（分组求解）本身只有 10 秒且有状态表跟踪，不需要缓存
05消息队列（Kafka / RabbitMQ / BullMQ） 唯一的异步需求是"分组求解不等 10 秒"，用一张 grouping_runs.status 表 + 前端轮询就能解决。为一张状态表引入一个中间件，是把简单问题复杂化的典型
06微服务架构 两个服务（web + algo）已经是按"语言边界"拆分的结果，这是必要的最小拆分。再往下拆（把认证、分组、归因拆成独立服务）只会带来分布式事务、链路追踪、跨服务鉴权三类新问题，而收益是零
07GraphQL 价值在于"前端自由组合字段"，但我们的字段组合在开发期就固定了。引入它要额外处理查询复杂度限制、缓存、鉴权粒度三个问题，换来的灵活我们用不上
08Prisma（若基座用 Drizzle） 基座已集成 Drizzle。换 ORM 意味着重写 schema、重建迁移历史、改掉全部查询代码，是一次纯粹的返工，且会失去跟随基座更新的能力
09NextAuth / Auth.js 基座已有轻量会话方案。更关键的是我们的角色是"课程级"的（同一学生不同课不同角色），NextAuth 的会话模型不容易表达这种结构，自己写反而简单
10本地部署大模型（Ollama / vLLM） 详见 T6。一句话：8GB 显存只能跑 7B 量化模型，做复杂结构化任务的质量差距明显，而 API 成本可忽略；同时会给答辩现场引入"本地服务起不来"的风险
11K8s / Docker Swarm 三个容器跑在一台机器上。K8s 的学习成本与运维复杂度，对单机三服务是纯负债。Docker Compose 一个文件搞定
12Electron / 原生 App 教师端是桌面宽屏，Web 就是最合适的载体；队员端用响应式 H5。打包成 App 只是给用户增加一次下载安装的摩擦，不解决任何实际问题

这 12 条怎么在答辩时转化成优势

如果评委问"技术上最有挑战的地方是什么"，一个有力的回答是：「最难的不是加什么，是不加什么。」然后举 PDF 解析这个例子——我们本来用 pymupdf 效果更好，但它是 AGPL，所以换成 pdfplumber；再举分组算法的例子——没有直接抄现成的开源实现，而是用 OR-Tools 重新建模。主动划边界的团队，比堆技术的团队更可信。

T14

可替换与锁定

哪些决定将来想换就能换，哪些换了要伤筋动骨。提前分清这两类，能避免在错误的地方纠结。

技术可替换性更换代价与建议
大模型服务商 极高 只改 base_url 与模型名，业务代码零改动。这正是选 OpenAI 兼容协议的价值。已在 llm.py 中通过环境变量隔离
PDF 解析库 极高 只要抽出纯文本，换任何库都不影响下游。若将来确定不上线，可换回 pymupdf 提升速度
图表与图形库 高 Recharts / Cytoscape / React Flow 都是纯展示层，输入数据来自接口。换库只改渲染组件，不动数据层
拖拽库 中 只影响分组工作台与看板两个页面，但交互逻辑需要重写。约 2–3 人天
对象存储 中 本地磁盘 → S3/OSS 需要抽一层存储接口。建议一开始就把文件读写封装成 storage.save() / storage.read()，这样将来换只改一个实现类
ORM 低 Drizzle → Prisma 要重写全部 schema 与查询。这是绑定在基座上的决定，选定时就已锁定
Web 框架 低 等同于重写整个前端。没有更换的可能，也不必考虑
数据库 低 JSONB 字段与全文索引都用了 PostgreSQL 独有能力。换 MySQL 需要改动多处
约束求解器 中 CP-SAT → 手写启发式算法：可以降级替换（规格书 S4.10 已有降级方案），但会失去"保证满足硬约束"这一核心保证。不建议替换
移动端载体 高 响应式 H5 → Taro 小程序，页面代码大部分可复用（同为 React）。这正是先做 H5 的原因：它是通向小程序的最短路径

一句话总结

本项目的技术选择可以分成两组：「基座锁定组」（Next.js、Drizzle、PostgreSQL——跟着 fork 走，不纠结）和「能力可换组」（模型、解析库、图表、存储——都通过接口或环境变量隔离，随时可换）。把纠结的时间花在分组工作台和贡献账本这两个真正的加分点上。

答辩时可能被问的三个技术问题，答案都在本文档里

  • 「为什么用约束求解器而不是遗传算法？」 → T4：CP-SAT 保证满足硬约束且给出可证明的最优解，手写 GA 至少 400 行且无法保证解合法。
  • 「为什么 AI 只用在大模型两个地方？」 → T1-03 与规格书 S6：能算的不要问模型。数值由公式算出，模型只会为既定数字编造理由。
  • 「有显卡为什么不用本地模型？」 → T6：8GB 显存只能跑 7B 量化模型，做复杂结构化任务质量差距明显；而 API 一学期成本可忽略，还避免了现场演示时本地服务起不来的风险。
