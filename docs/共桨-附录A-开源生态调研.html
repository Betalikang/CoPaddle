附录 A · 开源生态调研

这个赛道在开源世界是「零件齐全、没有整机」 对 GitHub 上现有开源项目的分类梳理、许可风险提示与可复用点标注。结论：没有任何一个项目把「AI 分组 → 任务拆解 → 实时重规划 → 贡献归因」串成闭环，这正是共桨的定位空间。

A.1

分组优化：最成熟的一类，参考价值最高

共桨 M2 模块（多目标最优分组）在这类项目里有大量现成实现可直接借鉴，从启发式到精确求解器都有。

项目技术栈 / 许可关键能力
gruepr/gruepr C++ / Qt
GPL-3.0		 遗传算法把 4–1000 人分成最优小组。官方自述 "inspired by CATME's team forming routine"。支持 15 类属性的组内同质/异质控制、防孤立女性与非主流群体学生、课表空闲重合度（含时区）、互斥与绑定约束。评分函数设计最完整
UTDallasEPICS/Teambuilder Python + TypeScript
生产级		 用 Google OR-Tools CP-SAT 约束求解器求全局最优。硬约束（每人必属一组、组规模 4–6）+ 软偏好（专业多样性、性别均衡、老队员优先、技能匹配、志愿优先级）。有完整 wiki 讲建模细节。这是最工业化的参考
smoab/teams-former Python + Eel
MIT		 遗传算法 + 网页前端。三个指标：组间 GPA 均衡、时间不冲突、组内技能不重复。结构简单、MIT 许可可自由使用，最容易直接改造
Bilin22/Forming-Optimal-Groups Python
课程项目		 三种算法对照实现：字母序 / 贪心 / 模拟退火。多伦多大学 CSC148 课程项目，适合当 baseline 与消融实验的对照组
BasselTharwat/TeamClusterAndForm Python + PyQt5 + pyvis 进化算法 + 社交网络图可视化 + 好友偏好匹配。可借鉴其"把关系画出来给教师看"的交互设计
nusoniclab.github.io Python
论文配套		 NSGA-II 多目标遗传算法同时优化"团队沟通成本"与"成员多样性"，且建立在真实社交网络之上。最贴近共桨「联系度 + 多样性」双目标命题。附论文与三套实证数据集

许可风险：gruepr 是 GPL-3.0 强 Copyleft

把 gruepr 的代码链接或修改进自己的产品，整个产品就要以 GPL-3.0 开源。参赛与后续商业化都建议只借鉴算法思想（遗传算法与评分函数的设计），不引入代码。若要用代码，优先选 MIT 的 smoab/teams-former 或自行实现。

A.2

同伴互评：有实现，但全部是主观评分

这类项目能直接给共桨 M6 提供数据模型参考，但它们有一个共同的局限——归因完全依赖学生自己填。

项目技术栈可复用点
ItzPabz/PeerEval Django + PostgreSQL 17 数据模型最完整：机构 → 院系 → 课程 → 学期 → 班级 → 选课 → 分组 → 评价作业。多租户架构、角色权限、批量名册导入导出、成绩导出。五个评价维度（工作贡献 / 团队互动 / 团队意识 / 工作质量 / 知识技能）
jetcom/peer_eval Node / 前后端分离 分阶段评价（1–5 个阶段）与截止日级联继承逻辑；评价热力图——一张图看出谁评了谁、谁没评。这个交互值得直接借鉴到教师端
imrohitvk/PeerEvaluation_V3 MERN + 可选 Python AI Engine 轻量、结构清晰，适合快速对照与二次开发起点

共同局限 = 共桨的差异点

所有开源互评系统的"贡献"来源都只有一条：学生自己填的问卷。没有一个做交付物级溯源。这意味着两件事：一是搭便车者只要会填表就能规避；二是数据模型里根本没有"产出物归属"这张表。共桨把产出物溯源作为第一类证据，是对这一类项目的结构性超越，而不是功能增量。

A.3

课程 / 项目全流程管理：最接近"整机"的一类

这类项目已经是一个完整系统了，但它们的短板惊人地一致——没有 AI 分组，也没有 AI 归因。

A.4

AI Agent 式项目管理：跨领域，但机制可迁移

这些项目管的是"AI 智能体团队"，不是"人类学生团队"。但它们的任务拆解、角色编排、阻塞检测机制可以整体迁移到共桨的 M3 与 M4。

项目可迁移的机制
sdi2200262/agentic-project-management Planner / Manager / Worker 三角色分工（与共桨的教师/队长/队员形成有趣映射）；规范驱动的产物（Spec / Plan / Rules 三份文档）；上下文 Handoff——当成员上下文耗尽时把工作记忆结构化移交。这个 Handoff 机制可以直接对应共桨的"重规划时的任务交接"
PriyankTyagii/ai-project-manager 四个专职 Agent：Planner（拆任务）/ Risk（监控阻塞与依赖）/ Motivation（停滞时推动）/ Report（自动日报）。事件驱动架构（Inngest）。Risk Agent 与 Motivation Agent 完全对应共桨的进度感知与"中立第三方催办"
kunwarVivek/mcp-github-project-manager Agent 注册与原子化认领任务（防重复、防冲突）、心跳存活监控、工作产物提交与互审、每人 token 预算与硬停。其中的"认领 + 心跳 + 互审"三件套，是把协作过程数据化的完整范式
MetaGPT / CrewAI / ChatDev 量级最大的角色化多智能体框架。把 SOP 编码进 prompt，让不同角色按流程协作。值得看的是它们如何定义角色边界与交接物，而不是直接使用

一个值得写进答辩的类比

多智能体系统里最难的问题不是"单个 agent 有多强"，而是"多个 agent 如何不重复劳动、不互相踩脚、不丢失上下文"。人类学生小组的失败模式几乎一模一样：重复劳动、依赖断裂、上下文（信息）不对称。共桨本质上是在给人类小组装一套多智能体编排层——这个类比能让评委瞬间理解你的产品在解决什么。

A.5

比代码更值钱：搭便车与贡献不均的实证研究

共桨的贡献归因模块需要一个"什么时候该报警"的阈值，和一个"能不能据此扣分"的伦理依据。这两件事都能从学术文献里直接拿到答案。

关键文献：不等贡献对学生软件工程团队的影响（JSS 2023）

可用的硬数字：当团队中最不活跃成员的贡献低于其应分担份额的 14% 时，团队就大概率会主观感知到贡献不均。这个 14% 可以直接做成共桨触发搭便车预警的、有研究支撑的阈值——答辩时能说出"我们的预警阈值不是拍的，来自一篇实证研究"，说服力完全不同。

同样重要的反向结论：该研究还发现，贡献不均与团队成绩、代码质量之间没有稳定的关联，且学生本身对相当程度的不均是有容忍度的。

这意味着什么：不能因为"贡献不均"就直接判罚。这条实证结论正是共桨「只给证据不给分」的直接依据——系统提供的是决策依据，是否扣分由教师结合任务性质判断。把这条写进方案，伦理立场就立住了。

两个好的理论视角

1. Amdahl 定律视角（CogSci 2024 / Cognition 2025）：研究者用分布式系统的效率模型解释社会惰化——当团队规模增大、工作量固定、资源（工具）有限时，个人贡献的边际影响下降，有时"少出力"是对效率的理性反应，而非道德缺陷。共桨可以用这个视角做一个很高级的产品决策：不要设计成"抓坏人"的工具，而是设计成"让每个人的边际贡献可见"的工具。

2. 社会惰化的经典量化：林格曼拉绳实验——个人单独拉力 63 kg，3 人组人均降至 53.5 kg，8 人组仅 31 kg。这个数字放在答辩 PPT 开场，比任何一句"小组作业有搭便车问题"都有冲击力。

相关仓库：emieczkowski/SocialLoafingEfficiency、emieczkowski/IdleCollaborators（均含数据与分析代码）

A.6

结论：四个明确的空白点

#空白点说明与机会
01 没有闭环 分组（gruepr、Teambuilder）、管理（TrackDev）、归因（PeerEval）各自独立，没有任何项目把四段串成一条流水线。共桨的核心价值就是这个"串联"
02 归因全是主观的 开源的"贡献"无一例外来自自评互评问卷。基于交付物版本溯源的归因，在整个开源生态里是真空
03 没有中文高校场景 全部是英文界面 + 海外教学语境，没有对接教务成绩、班级、综测、学分这类中式教学管理要素
04 没有一个是 LLM 原生的 分组用遗传算法或约束求解器，管理用传统看板，AI 至多做自动评分。用 LLM 做任务语义拆解、依赖推断、冲突归因、自然语言解释的，一个都没有

可复用清单（按性价比排序）

  • 分组建模 → 抄 UTDallasEPICS/Teambuilder 的 CP-SAT 约束建模（工业级、有文档）
  • 双目标优化 → 参考 SONIC Lab 的 NSGA-II（沟通成本 vs 多样性，最贴合命题）
  • 快速起步 → smoab/teams-former（MIT，结构简单，三个指标已经对齐共桨需求）
  • 产品骨架 → trackdevel 的角色权限、任务拆解与自动评估设计
  • 数据模型 → ItzPabz/PeerEval 的课程层级关系
  • 交互点子 → jetcom/peer_eval 的评价热力图；TehtavaApp 的"AI 评分 + 教师确认"两档模式
  • 预警阈值 → JSS 2023 的 14% 应分担份额；伦理依据 → 该研究的"不均与成绩无稳定关联"

许可红线（必读）

  • GPL-3.0 gruepr —— 强 Copyleft。引入代码即要求整个产品以 GPL-3.0 开源。只借鉴思想，不引代码
  • MIT smoab/teams-former —— 可自由使用、修改、商用，保留版权声明即可。优先选这一类
  • 其余多数项目未在 README 中明确声明许可（如 TrackDev、ProjecTrack），属于"默认保留全部权利"，商用前必须逐一确认
  • CATME 的 EULA 明确禁止 "attempt to imitate, derive or discover" 其软件 —— 建议在方案书中主动声明"独立设计"，并避免逐条对照其功能清单
